Resources are files stored in a project so that workflows can consume them at run time. Common resource types include datasets (tabular data, sensor readings, simulation outputs) and model artefacts (trained weights, calibration files, configuration objects). Resources are scoped to a specific project, and every time you upload a new file for the same resource a new version is created automatically. Workflows always reference the latest version unless you request a specific one.

## What resources contain

<CardGroup cols={2}>
  <Card title="Datasets" icon="table">

    input. Upload once, reuse across many workflow runs.

  <Card title="Model artefacts" icon="cube">
    Serialised models, weight files, and calibration configs produced by
    training runs. Store them as resources so downstream workflows can load
    them without re-training.

## Managing resources

Resources are created, listed, and managed via the **Uncertainty Engine web UI** or the **REST Resource API**. The Resource API authenticates with the `X-Resource-Service-Token` header and exposes endpoints for uploading file versions, listing resources, and deleting them.

For example, to list all resources in a project:

```http
GET /api/projects/{project_id}/resources
X-Resource-Service-Token: <your-token>
```

To upload a new resource (or a new version of an existing one):

```http
POST /api/projects/{project_id}/resources
X-Resource-Service-Token: <your-token>
Content-Type: multipart/form-data

resource_type=dataset
file=@data/measurements.csv
```

See the [Resource API reference](/api-reference/rest-resources) for the complete list of endpoints, request schemas, and response formats.

<Tip>
  Use consistent `resource_type` values across your team (for example,
  `"dataset"` and `"model"`) so that resource listings stay organised and
  workflows can rely on a predictable naming convention.
</Tip>

## Resource versioning

Each upload for an existing resource creates a new version rather than overwriting the previous one. This means:

- Previous versions remain accessible by specifying the version number in the API request.
- Workflows that reference a resource without a pinned version automatically use the latest upload.
- You can roll back to an earlier version by requesting it explicitly via the Resource API.

<Note>
  Version numbers are integers that increment from `1` with each upload.
  The resource object returned by the API includes the current `version` field
  so you always know which revision you are working with.
</Note>

## Reference resources in SDK calls

When running a workflow that uses resource-management nodes, the project ID and resource identifiers are resolved automatically from the workflow definition. The project ID you pass to `client.run_workflow()` determines which project's resources are accessible.

```python
from uncertainty_engine import Client

client = Client()
client.authenticate()

result = client.run_workflow(
    project_id="your_project_id",
    workflow_id="your_workflow_id",
    inputs=[],
)
print(result.outputs)
```

<Warning>
  Deleting a resource removes all its versions permanently. Any workflow that
  references the deleted resource will fail at run time. Update or redeploy
  affected workflows before removing a resource.
</Warning>

For details on how resource-management nodes inside a workflow read and write project resources at run time, see the [Resource Management nodes](/nodes/resource-management) reference.
